# 이메일 기능

## 구현 목표

GroupWorks의 이메일 기능은 사내 사용자가 서로 메일을 주고받을 수 있도록 만든 기능입니다.
단순한 메시지 저장을 넘어서 수신함, 발신함, 중요 메일함, 휴지통, 첨부파일, 검색, 알림까지 포함했습니다.

## 왜 MongoDB를 사용했는가?

메일 데이터는 일반적인 사원 정보나 부서 정보와 성격이 다릅니다.

메일은 다음과 같은 특징을 가집니다.

- 제목, 내용, 발신자, 수신자, 참조자 등 필드가 다양합니다.
- 첨부파일 정보가 함께 저장됩니다.
- 읽음 여부, 중요 여부, 휴지통 여부 등 상태값이 자주 변경됩니다.
- 수신함, 발신함, 중요 메일함, 휴지통 등 조회 방식이 다양합니다.
- 하나의 메일을 문서 단위로 저장하고 조회하기 좋습니다.

이런 이유로 이메일 기능에는 관계형 DB가 아닌 문서 기반 저장소인 MongoDB를 사용했습니다.
또한 프로젝트를 진행하면서 NoSQL을 학습해보고 싶은 목적도 있었습니다.

## 이메일 작성 요청 흐름

```text
사용자가 메일 작성
→ 세션에서 발신자 정보 조회
→ 수신자 이메일로 사원 정보 조회
→ 참조자 이메일이 있으면 참조자 정보 조회
→ 메일 발송 시간 설정
→ 메일 상태값 초기화
→ 첨부파일 목록 조회
→ 메일과 첨부파일 저장
→ 수신자에게 알림 전송
→ 참조자가 있으면 참조자에게도 알림 전송
→ 보낸 메일함으로 redirect
```

메일 작성 시에는 세션에서 발신자 정보를 가져와 발신자 ID, 이메일, 이름을 설정했습니다.
수신자와 참조자는 이메일을 기준으로 사원 정보를 조회해 ID와 이름을 함께 저장했습니다.

## 메일함 조회 흐름

### 수신 메일함

```text
수신 메일함 접근
→ 세션에서 로그인 사용자 이메일 조회
→ 검색 조건 확인
→ 제목 검색이면 제목 기준 조회
→ 발신자 검색이면 발신자 이름 기준 조회
→ 검색 조건 없으면 전체 수신 메일 조회
→ Page 객체를 Model에 담아 화면 렌더링
```

수신 메일함에서는 로그인한 사용자의 이메일을 기준으로 직접 받은 메일과 참조된 메일을 함께 조회했습니다.

### 발신 메일함

```text
발신 메일함 접근
→ 세션에서 로그인 사용자 이메일 조회
→ 검색 조건 확인
→ 제목 검색이면 제목 기준 조회
→ 수신자 검색이면 수신자 이름 기준 조회
→ 검색 조건 없으면 전체 발신 메일 조회
→ Page 객체를 Model에 담아 화면 렌더링
```

발신 메일함에서는 로그인한 사용자가 보낸 메일을 기준으로 조회했습니다.

## 첨부파일 저장 흐름

```text
메일 저장
→ 메일 ID 생성
→ uploadDir/mail-files/{mailId} 디렉터리 생성
→ 첨부파일 목록 순회
→ 빈 파일 제외
→ 확장자 검사
→ 허용된 확장자만 서버 디렉터리에 저장
→ 파일명과 파일 경로를 MailAttachmentFile 객체로 저장
→ 메일 엔티티에 첨부파일 정보 반영
→ MongoDB에 다시 저장
```

첨부파일은 메일 ID별 디렉터리를 만들고, 허용된 확장자만 저장하도록 제한했습니다.
메일 첨부파일은 사용자가 직접 파일을 업로드하는 기능이므로 최소한의 파일 타입 검증이 필요하다고 판단했습니다.

## 구현하면서 고민한 점

메일 데이터를 RDB에 저장할지 MongoDB에 저장할지 고민했습니다.
RDB는 관계와 정합성 관리에 강하지만, 메일은 하나의 문서처럼 다루기 좋은 데이터입니다.
메일 제목, 내용, 발신자, 수신자, 참조자, 첨부파일, 상태값을 하나의 문서로 묶어 저장하면 조회 구조를 단순하게 가져갈 수 있습니다.

다만 MongoDB가 항상 정답은 아닙니다.
검색 조건이 복잡해지거나, 사원/부서 데이터와 강하게 조인해야 하는 상황이 많다면 RDB가 더 편할 수도 있습니다.

## 장점

- MongoDB를 사용해 문서 기반 데이터 저장을 경험할 수 있었습니다.
- 메일과 첨부파일 정보를 하나의 흐름으로 다룰 수 있었습니다.
- 수신함, 발신함, 중요 메일함, 휴지통 등 다양한 조회 조건을 구현했습니다.
- 메일 발송 이후 알림 기능과 연결해 업무 시스템다운 흐름을 만들었습니다.

## 아쉬운 점과 개선 방향

- 첨부파일 저장 시 파일명 충돌 방지 처리가 더 필요합니다.
- 파일 확장자뿐 아니라 MIME type 검증도 추가하면 더 안전합니다.
- 대용량 파일 업로드 제한, 바이러스 검사, 다운로드 권한 검증을 추가하면 더 실무적인 구조가 됩니다.
- MongoDB와 RDB를 함께 사용할 때 데이터 정합성을 어떻게 관리할지 더 고민할 필요가 있습니다.
